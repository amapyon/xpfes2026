# device1 プログラム生成用プロンプト

UIAPduino Pro Micro CH32V003 V1.4、
ch32fun、必要な場合はrv003usbを使って、
自由制作device1のプログラム一式を生成してください。

初心者が短時間で

「ビルドする → 書き込む → 動かす」

ところまで到達できることを優先してください。

完全な実装根拠や実機確認結果がすべて揃うまで待つのではなく、
安全に試せる範囲では、合理的な実装を選んでプログラムを生成してください。

---

## 今回の入力

* REQUIREMENTS.md
* WIRING.md

利用経路:

ローカル操作型 / Web・手動受け渡し型

## 基本方針

REQUIREMENTS.mdを、

「何を作るか」

の正本として扱ってください。

WIRING.mdを、

「どの部品をどのGPIOへ接続するか」

の正本として扱ってください。

プログラム生成段階では、
REQUIREMENTS.mdとWIRING.mdは原則として読み取り専用として扱い、
内容を書き換えないでください。

ただし、これらはソフトウェア内部の詳細設計を
すべて事前確定するための契約書ではありません。

ソフトウェア実装上の細かな事項が書かれていない、
または「要確認事項」として残っている場合でも、
安全性や物理配線に影響しない内容であれば、
生成AI自身で合理的な方法を選んで実装してください。

例えば次は生成AIが決めて構いません。

* 変数名
* 関数構成
* 状態管理方法
* デバウンス方法
* デバウンス時間
* ポーリング周期
* エンコーダーの状態遷移処理
* ソフトウェア上の回転方向反転方法
* HID Reportを送るタイミング
* USB HID Usage
* USB Report Descriptor
* Report ID
* Report長
* Reportのデータ構造
* キー押下とキー解放に相当するReport送信方法
* USB Descriptorの実装方法
* 軽微なタイミング値
* タイムアウト値
* エラー処理方法
* 軽微な初期値

利用者の意図、使用部品、物理配線、
安全性を変えない限り、
これらを確認するためにプログラム生成を停止する必要はありません。

## 実装判断の優先順位

複数の実装方法がある場合は、
次の順序で選んでください。

1. 安全に試せる
2. Devkitの既存構成でビルドできる
3. Windows 11とmacOS Apple Siliconの差異が小さい
4. 既存の演習・PoC・ライブラリ構成を流用できる
5. 初心者が理解しやすい
6. 実機確認で問題があった場合に修正しやすい
7. 追加インストールを必要としない
8. コードが単純である
9. 高度・高機能である

高度な実装より、
ワークショップ中に動作確認しやすい最小実装を優先してください。

## 利用できる開発基盤

原則として次を使用してください。

### MCU

* CH32V003
* ch32fun

### USBを使う場合

* rv003usb

Devkitで採用していないUSBスタックを、
新たに導入しないでください。

例:

* TinyUSB
* Arduino USB API
* WCH HAL USB

Devkit外の追加ライブラリを
インターネットからインストールすることを前提にしないでください。

標準USB HID機能を新しく実装することと、
新しいUSBスタックや外部ライブラリを追加することは別です。

rv003usbを使ったまま、
必要なHID Report DescriptorやReport構造を新しく設計することは許可します。

## 最初に確認すること

REQUIREMENTS.mdとWIRING.mdを読み、
次を確認してください。

1. 作りたい動きが分かる
2. 使用する部品が分かる
3. 物理的なGPIO配線が分かる
4. 電源、GND、極性などに危険な矛盾がない
5. CH32V003と採用済み部品で要求機能を実現できる見込みがある

問題がなければ、
すぐプログラム生成へ進んでください。

人による承認状態、確認者、確認日などは要求しないでください。

REQUIREMENTS.mdまたはWIRING.mdに
`要確認事項`が残っていること自体は、
プログラム生成を停止する理由にはなりません。

`要確認事項`の内容を確認し、

* 安全・物理配線に関する問題
* ソフトウェア実装上の未確定事項

を区別してください。

## プログラム生成を停止する条件

原則として、
まず動作確認できるプログラムを生成することを優先してください。

プログラム生成を停止するのは、
次の場合に限定してください。

* 電源、GND、GPIO、極性、部品定格などに重大な安全上の問題がある
* REQUIREMENTS.mdとWIRING.mdで物理構成が矛盾しており、どちらを採用すべきか合理的に判断できない
* 必要な物理GPIOが決まっておらず、ソフトウェアだけでは解決できない
* 抵抗、ダイオード、トランジスタ、MOSFETなど必要な保護・駆動回路が不足しており、そのまま動作させると危険である
* 要求された機能がCH32V003または採用済みハードウェアでは実現不可能である
* プログラム生成を続けることで、UIAPduino、部品、USB接続先PCを破損する可能性がある
* 安全に関係する物理的な前提について、合理的な判断ができない

WIRING.mdの`設計結果`が`要確認`の場合も、
その文字列だけを理由に停止しないでください。

`要確認`の理由を読み、

* 物理配線や安全性が未確定なら停止
* ソフトウェア実装だけが未確定なら生成を続行

してください。

---

## 次の理由だけでは停止しないこと

次のような理由だけで
プログラム生成を停止しないでください。

* 同一機能の参考演習・PoCがない
* 完全一致するサンプルコードがない
* 必要な機能が既存演習には存在しない
* USB Report Descriptorを新しく作る必要がある
* HID Usageを選ぶ必要がある
* Report IDを決める必要がある
* Report長を決める必要がある
* Report構造を決める必要がある
* USB Descriptorを既存例からそのまま流用できない
* デバウンス方法が決まっていない
* デバウンス時間が決まっていない
* ポーリング周期が決まっていない
* エンコーダーの回転方向が実機未確認
* S1/S2のソフトウェア上の論理設定が実機未確認
* 軽微なタイミング値が決まっていない
* README.mdに記載できる程度の実機確認事項が残っている
* REQUIREMENTS.mdまたはWIRING.mdの`要確認事項`欄にソフトウェア実装上の未確定事項が残っている

これらは生成AI自身で合理的な初期値や実装方式を選び、
プログラム生成を続けてください。

実機で確認する必要がある場合は、
README.mdに確認方法と修正方法を記載してください。

## 参考実装の扱い

REQUIREMENTS.mdまたはWIRING.mdに
参考演習・PoCが記載されている場合は、
できるだけその実装を起点にしてください。

ただし、
参考演習・PoCは、

「そこに存在する機能だけを実装してよい」

という制限ではありません。

既存実装は主に次の目的で利用してください。

* ch32funの初期化方法
* GPIO初期化方法
* rv003usbの組み込み方法
* USB割り込み処理
* USB Report送信処理
* Makefile
* funconfig.h
* usb_config.h
* Devkit固有のビルド方法
* デバウンスなど確認済みの処理
* エンコーダーなど確認済みの入力処理
* PC側プログラムとの通信方式

必要な機能が参考実装に存在しない場合は、
既存コードの構造を利用しながら、
不足している部分を新しく実装してください。

例えば次は許可します。

* Keyboard HIDしか参考実装がない状態からConsumer Control HIDを作る
* Vendor-defined HIDしか参考実装がない状態から標準HID Usageを使う
* 新しいHID Report Descriptorを作る
* 新しいReport構造を作る
* 新しいUsageを追加する
* 既存のGPIO入力処理と別のUSB HID機能を組み合わせる

既存サンプルに完全一致しないことだけを理由に、
生成を停止しないでください。

## USB実装で守ること

USBを使用する場合は、
rv003usbの既存APIとDevkit内の構成を利用してください。

存在しないrv003usb API、
存在しないヘッダー、
存在しない関数を推測して使用しないでください。

ローカル操作型では、
実際のrv003usbソースや参考実装を確認してください。

Web・手動受け渡し型では、
受け渡されたrv003usb関連ファイルや参考実装を優先してください。

一方、
HID標準上必要となる次の内容は、
既存演習に完全一致するものがなくても
新しく設計して構いません。

* Usage Page
* Usage
* Collection
* Report Descriptor
* Report ID
* Reportサイズ
* Input Report
* Output Report
* Feature Report
* Report送信タイミング

つまり、

「rv003usbの存在しないAPIを創作する」

ことは禁止しますが、

「rv003usbで使用する新しいHID Report Descriptorを設計する」

ことは許可します。

## USB HIDの新規設計

REQUIREMENTS.mdで要求されたUSB HID機能が
CH32V003とrv003usbで実現可能と判断できる場合は、
既存演習に同一のDescriptorが存在しなくても
プログラム生成を続けてください。

必要に応じて生成AIが次を設計してください。

* HID Usage Page
* HID Usage
* Report Descriptor
* Report ID
* Reportサイズ
* ReportのC構造
* Input / Output / Feature Report
* Report送信タイミング
* 押下と解放に相当するReport
* usb_config.hの定義

USB HID仕様として一般に定義されている機能については、
既存PoCに完全一致するコードが存在することを
必須条件としません。

例えばConsumer Controlの

* Volume Increment
* Volume Decrement
* Mute

などは、
既存演習に同一実装がなくても
新しく実装して構いません。

## 外部情報の扱い

一般的なC言語、USB HID、HID Usageなどの知識を
ソフトウェア設計に利用して構いません。

外部資料を確認できる環境では、
必要に応じて公式仕様や一次資料を確認して構いません。

ただし、

* 新しい外部ライブラリを追加する
* Devkit外のUSBスタックを導入する
* 参加者に追加インストールさせる

ことは避けてください。

外部情報を利用できないことだけを理由に、
既存Devkitと一般的な仕様知識で安全に実装可能なプログラムの生成を
停止しないでください。

## 実機で簡単に確認できる事項

次のような事項は、
安全に実機確認でき、
少ない変更で修正できる場合、
プログラム生成を停止しないでください。

例:

* エンコーダーの時計回り / 反時計回りが逆
* S1/S2の論理状態
* 軽微なチャタリング
* デバウンス時間
* ポーリング周期
* 1操作あたりのReport送信回数
* 軽微なタイミング調整

合理的な初期値を選んで実装してください。

可能であれば、
調整値は定数や`#define`など、
初心者でも変更箇所が分かりやすい形にしてください。

例えば回転方向を変更する必要がありそうな場合は、
コード全体を書き換えなくても済む構造を優先してください。

README.mdには、

### 実機確認ポイント

として、

1. 期待する動作
2. 確認方法
3. 期待と逆だった場合の対処
4. 変更する定数またはコード位置

を記載してください。

## ワークショップ共通のUSB識別子

USBアプリケーションのVIDとPIDは
参考実装の値をそのまま流用せず、
必ず次に固定してください。

* VID: `0x1209`
* PID: `0x0001`

`1209:0001`はpid.codesの共有テスト用識別子であり、
世界で一意ではありません。

教育目的の試作と、
このワークショップ内のテストだけに使用します。

製品、製造、販売、一般向け再配布には使用しません。

VIDとPIDを定義または直接埋め込む

* ファームウェア
* PC側プログラム
* 設定ファイル

には、
この制限を示す警告コメントを必ず記載してください。

Product文字列は
演習ごと、参加者の自由制作ごとに設定します。

自由制作では、
REQUIREMENTS.mdのデバイス名を基にした
識別しやすいProduct文字列にしてください。

PC側プログラムがProduct文字列を使用する場合は、
ファームウェア側と同じ文字列を使用してください。

ブートローダーの`1209:B803`は変更しません。

通常アプリケーションの`1209:0001`と
混同しないでください。

## プログラムで守ること

* 主ソースは`device1.c`
* ch32funを使用する
* WIRING.mdのGPIOと一致させる
* WIRING.mdの物理配線を変更しない
* 起動直後に意図しないGPIO出力を出さない
* 起動直後に意図しないUSBキー入力やConsumer Control指示を送らない
* スイッチには必要に応じてデバウンスを入れる
* エンコーダーには必要に応じてチャタリング対策を入れる
* WIRING.mdで確定しているプルアップ / プルダウンを使用する
* USB不要ならrv003usbを追加しない
* PC側プログラム不要ならhost/を作らない
* REQUIREMENTS.mdで要求していない機能を勝手に増やさない
* 実機未確認の事項を「確認済み」と表現しない
* 存在しないライブラリやAPIを創作しない
* 初心者が変更する可能性のある調整値は、可能なら定数としてまとめる

## README.mdの「実装上の判断」

REQUIREMENTS.mdやWIRING.mdで未確定だった事項を
生成AIが決定した場合は、
README.mdに簡潔に記録してください。

例:

```text
## 実装上の判断

- KEYはActive Lowとして実装
- KEYのデバウンス時間は20ms
- エンコーダーは状態遷移方式で方向を判定
- Consumer ControlはReport IDなしの1バイトReportとして実装
- 音量Up / Down / Muteは押下Reportの後に解放Reportを送信
```

ここに記録することによって、
ソフトウェア上の未確定事項を理由に
プログラム生成を停止する必要はありません。

## README.mdの「実機確認ポイント」

実機でしか最終判断できない事項がある場合は、
次のように記載してください。

```text
## 実機確認ポイント

### エンコーダーの回転方向

期待:

- 時計回り → 音量Up
- 反時計回り → 音量Down

逆になった場合:

`device1.c`の回転方向設定を変更してください。

物理配線を変更する前に、
まずソフトウェア設定で修正できるか確認してください。
```

実機未確認であることは問題ではありません。

ただし、
確認していない内容を
「実機確認済み」と表現しないでください。

## ローカル操作型

ローカル操作型では、
Devkit内のファイルを実際に読んでください。

最低限確認するもの:

* workspace/ai/BOARD_FOR_AI.md
* workspace/parts/PARTS_FOR_AI.md
* workspace/my/device1/REQUIREMENTS.md
* workspace/my/device1/WIRING.md
* workspace/ai/MY_DEVICE_TEMPLATE/
* 必要な参考演習・PoC

USBを使用する場合は、
必要に応じて次も確認してください。

* workspace/deps/rv003usb/
* 参考演習のusb_config.h
* 参考演習のfunconfig.h
* 参考演習のMakefile
* 参考演習のUSB送信処理

編集は原則として、

`workspace/my/device1`

だけに限定してください。

次は参照専用です。

* workspace/parts/
* workspace/ai/
* workspace/exercises/
* workspace/deps/

REQUIREMENTS.mdとWIRING.mdも
プログラム生成段階では原則として変更しないでください。

## ローカル操作型のビルド確認

ファイル生成後は可能なら次を実行してください。

```sh
make clean
make
make size
```

ビルドエラーが出た場合、
REQUIREMENTS.mdや物理配線を変更しなくて済む範囲なら、
生成AI自身で修正して再ビルドしてください。

例えば次は利用者へ確認せず修正して構いません。

* include不足
* コンパイルエラー
* 型の不一致
* 未使用または誤った関数名
* Makefileの参照方法
* Descriptorの配列長
* Report構造とサイズの不一致
* 既存rv003usb APIへの適合

エラーごとに利用者へ確認を求める必要はありません。

物理配線の変更が必要になった場合だけ停止してください。

## 書き込みについて

ローカル操作型でも、
実際の書き込みを自動的に行う必要はありません。

`make flash`を実行する場合は、
UIAPduinoが適切な書き込み待機状態であることが確認できる場合に限ってください。

特に自由制作では、

1. 配線確認
2. ビルド
3. サイズ確認
4. 参加者による配線再確認
5. 書き込み
6. 実機確認

の順序を優先してください。

生成AIが実際に書き込みを行っていない場合は、

「書き込み成功」

とは表現しないでください。

## Web・手動受け渡し型

AI_HANDOFF_MANIFEST.mdまたはAI_HANDOFF.mdがある場合は、
そこに含まれる資料を使用してください。

受け渡された参考演習・PoCがある場合は
必要な部分を確認してください。

参考演習に目的の機能そのものが存在しなくても、
既存のch32fun / rv003usb構成を利用して
新しい機能を実装して構いません。

受講者PC上で実際に、

* ビルドした
* 書き込んだ
* USB認識を確認した
* 実機動作を確認した

とは表現しないでください。

Web上でコードを生成できたことと、
受講者PC上で動作確認できたことを区別してください。

## Web・手動受け渡し型の成果物

可能なら完成した、

`device1.zip`

を生成してください。

ZIP直下は`device1/`としてください。

正しい例:

```text
device1.zip
└── device1/
    ├── README.md
    ├── REQUIREMENTS.md
    ├── WIRING.md
    ├── Makefile
    ├── device1.c
    └── funconfig.h
```

USBを使う場合は必要に応じて
`usb_config.h`などを追加してください。

ZIPを生成できない場合は、
必要な全ファイルの全文を
1ファイルずつ出力してください。

初心者向け標準手順では、
差分だけ、
変更箇所だけ、
パッチだけを出力しないでください。

## BUILD_ERROR.txtがある場合

Web・手動受け渡し型で
BUILD_ERROR.txtが提供された場合は、
その内容を確認してください。

REQUIREMENTS.mdやWIRING.mdの物理配線を
変更しなくて済むエラーであれば、
生成AI自身でコードを修正してください。

例えば、

* コンパイルエラー
* リンクエラー
* include不足
* API名の誤り
* Descriptorサイズ不一致
* Reportサイズ不一致
* Makefileの問題

は修正対象です。

修正版は一部差分ではなく、
完成したdevice1一式として生成してください。

## 自己点検

生成後は次を確認してください。

### 要件

* REQUIREMENTS.mdの作りたい動きを実現している
* REQUIREMENTS.mdの完成条件に対応している
* REQUIREMENTS.mdで要求していない機能を勝手に増やしていない

### 配線

* WIRING.mdのGPIOと一致している
* WIRING.mdの物理配線を変更していない
* USB予約GPIOと競合していない
* 起動直後が安全な状態になっている

### コード

* 存在しないヘッダーを使っていない
* 存在しないライブラリを使っていない
* 存在しないrv003usb APIを創作していない
* 未定義関数や未定義シンボルがない
* 調整が必要な値は可能なら分かりやすく定義している

### USB

USBを使用する場合:

* rv003usbを使用している
* DescriptorとReport送信コードが整合している
* Report IDの有無がコード全体で一致している
* Reportサイズが一致している
* 起動直後に意図しないReportを送らない
* 必要なら押下後に解放相当Reportを送っている
* VID / PIDがワークショップ指定値になっている
* Product文字列が用途を識別できる
* テスト用VID / PIDの警告コメントがある

### Makefile

* Devkitの構成に合っている
* OS固有の絶対パスがない
* `make`
* `make size`
* `make flash`

を利用できる構成になっている

### README

* 初心者が次の操作を判断できる
* 実機未確認事項を明示している
* 実機確認方法が書かれている
* 問題が起きた場合の簡単な調整方法が書かれている

## 不確定事項の扱い

生成後に不確定事項が残っていても、
次の3種類に分類してください。

### A. 安全・物理配線に関する問題

例:

* 電源電圧不明
* GPIO接続不明
* 部品極性不明
* 必要な保護回路不足

この場合は生成を停止してください。

### B. ソフトウェア設計上の未確定事項

例:

* HID Report Descriptor
* Report ID
* Report長
* デバウンス方法
* ポーリング周期
* エンコーダー処理方法

この場合は、
生成AIが合理的に決定して生成を続けてください。

### C. 実機確認で調整できる事項

例:

* エンコーダー方向
* デバウンス時間
* 軽微なタイミング
* 入力の感触

この場合は、
合理的な初期値で生成し、
README.mdに確認・調整方法を記載してください。

## 最終判断フロー

次の考え方で判断してください。

```text
REQUIREMENTS.md / WIRING.mdを読む
        ↓
安全上・物理上の重大な問題がある？
 ├─ YES → 停止
 └─ NO
        ↓
必要な物理配線が判断できる？
 ├─ NO → 停止
 └─ YES
        ↓
CH32V003 + 採用済み部品で実現可能？
 ├─ NO → 停止
 └─ YES
        ↓
ソフトウェア仕様に未確定事項がある？
 ├─ YES → 生成AIが合理的に決定
 └─ NO
        ↓
既存サンプルがある？
 ├─ YES → できるだけ流用
 └─ NO → 既存Devkitの構造を使って新規実装
        ↓
プログラム生成
        ↓
実機確認が必要な点をREADME.mdへ記録
```

「既存サンプルがない」

と

「実現できない」

を混同しないでください。

## 出力

安全上または物理配線上の重大な問題がなく、
要求機能を実装できる見込みがある場合は、
最初に、

`プログラム生成OK`

と示し、
成果物を生成してください。

ソフトウェア上の未確定事項が残っていても、
生成AI自身で合理的に決定できる場合は
`要確認`として停止しないでください。

本当に利用者または講師の判断が必要な
安全・物理配線上の問題がある場合だけ、

`要確認`

または

`配線修正が必要`

として停止してください。
